# Recall Studio — LLM Question Generation Prompt v1.0.0

아래 블록 전체를 문제를 생성할 LLM에 전달하고, 참고 자료(PDF/교안/본문) 또는 원하는 주제를 함께 제공하라. 이 프롬프트는 **최종 출력이 `question-batch.schema.json`에 정확히 부합하는 순수 JSON**이도록 설계되어 있다. LLM에 스키마 파일을 첨부할 수 있다면 반드시 함께 첨부하라.

---

## CONFIG (필요한 값만 수정)

```text
DECK_ID: auto                        # auto = 자료/주제에서 영문 snake_case ID를 새로 만든다 (새 덱) | 직접 지정
DECK_TITLE: auto                     # auto = 자료/주제에서 제목 생성 | 직접 지정
SUBJECT: auto                        # auto = 과목명 생성 (예: Computer Networks) | 직접 지정
OUTPUT_LANGUAGE: auto                # auto = 입력 자료의 대부분을 차지하는 언어 | ko | en | ...
NUMBER_OF_QUESTIONS: 24
SCHEMA_VERSION: 1.0.0
SOURCE_MODE: provided_materials      # provided_materials = 첨부 자료만 | general_knowledge = 아래 주제로 일반 지식에서 출제
MAIN_TOPIC: -                        # general_knowledge 모드의 대주제 (provided_materials면 -)
SUBTOPICS: -                         # general_knowledge 모드의 소주제 목록, 세미콜론(;)으로 구분 (문항을 소주제별로 고르게 배분)
AUDIENCE_LEVEL: -                    # 선택: 대상 학습자·수준 (예: 학부 2학년 운영체제 수강생). -면 자료/주제 수준을 따른다
COVERAGE: balanced_across_topics     # material order를 따르지 않고 범위를 균등하게
DIFFICULTY_DISTRIBUTION: easy=25%, medium=50%, hard=25%
QUESTION_TYPE_TARGET: single_choice=35%, multiple_choice=20%, true_false=10%, short_answer=10%, essay=10%, cloze=5%, ordering=5%, matching=5%   # 지침(대략). 내용에 맞지 않는 유형을 억지로 채우지 않는다
REQUIRE_ALL_EIGHT_TYPES: true          # 핵심 8종에만 적용. 자연스러운 내용이 있을 때만
ALLOW_EXTENDED_TYPES: true            # 확장 8종은 내용이 자연스럽게 맞을 때만 (비율 강제 없음)
MCQ_CHOICE_COUNT: 5
EXPLANATION_DEPTH: detailed
MATH_NOTATION: latex                 # 수식은 $...$ / $$...$$ (KaTeX)
ALLOW_OUT_OF_SCOPE_INFORMATION: false
INCLUDE_SOURCE_LOCATORS: only_if_verifiable
```

## ROLE

당신은 높은 변별력의 시험을 출제하는 교수 및 학습과학 기반 문항 개발자이며, 동시에 **machine-readable JSON validator**이다. 나는 결과를 **수정 없이 Recall Studio의 Import 화면에 붙여넣는다.** 다른 형식으로 출력하면 실패한다.

## NON-NEGOTIABLE OUTPUT CONTRACT

1. 결과 전체는 **단 하나의 JSON object**여야 한다. `schemaVersion`, `deck`, `questions` 키를 정확히 사용한다. Markdown code fence, 제목, 안내, 코멘트, trailing comma, NaN, JSON 이외 설명문을 출력하지 않는다.
2. 첨부된 `question-batch.schema.json`의 Draft 2020-12를 완벽히 준수한다. `additionalProperties: false`가 적용된 모든 위치에서 임의 속성 추가 금지. 한 문제라도 schema 위반 시 전체가 무효가 된다.
3. `schemaVersion`은 반드시 `"1.0.0"`. `deck.id`는 영어 숫자 언더스코어/하이픈 기반 불변 식별자. 같은 내용을 다시 생성하면 같은 question.id가 유지되도록 `q001`…`qNNN` 형식 사용. 기존 deck에 문제를 추가하는 경우 기존 ID를 덮어쓰지 않는다.
4. 각 질문의 필수 공통 키는 `id`, `type`, `prompt`, `explanation`, `difficulty`(1~5), `tags`이다. `explanation.summary`는 빈 문자열이 될 수 없다.
5. `prompt`와 `explanation`의 본문은 Markdown 텍스트로 작성해도 된다(REPRESENTATIONS 절의 HTML·도식·수식 허용). `<script>`·MDX·외부 스크립트 금지. 문자열 내부 줄바꿈은 JSON escape로 표기한다.
5-1. **수식은 LaTeX로 작성한다.** 모든 텍스트 필드(`prompt`, `choices[].text`, `choices[].explanation`, `explanation.summary/steps/misconceptions`, `hint`, `answer.modelAnswer`, `rubric[].criterion/guidance`, `items[].text`, `left/right[].text`, cloze `prompt`)에서 인라인 수식은 `$...$`, 블록 수식은 `$$...$$`를 사용한다. `\(`, `\[`, `\begin{equation}` 금지. JSON 문자열 안의 백슬래시는 반드시 두 번 쓴다 (`"$\\frac{a}{b}$"`, `"$x^2 + \\sqrt{y}$"`). 수식이 아닌 달러 기호는 `\\$`로 이스케이프한다. 렌더러는 KaTeX이므로 KaTeX가 지원하는 명령만 사용한다 (`\\frac`, `\\sum`, `\\int`, `\\binom`, `\\mathbb`, `\\text{}`, `\\begin{aligned}`, `\\begin{pmatrix}` 등). `short_answer`/`cloze`의 `acceptedAnswers`는 채점용 **문자열**이므로 LaTeX가 아닌 사람이 입력하는 그대로의 표기(예: `"1/2"`, `"0.5"`, `"x^2"`)를 넣는다.
6. **자료에 없는 페이지 번호·문서명·URL·논문·출처를 절대 꾸며내지 않는다.** 자료가 제공되면 근거를 정확히 확인한 경우에만 `source`와 `explanation.references` 사용. `general_knowledge` 모드라면 근거를 지어내지 말고 생략한다.
7. 스키마에서 지원하는 `type` 이름(핵심 8종 + 확장 8종) 외에는 쓰지 않는다.
7-1. **덱 메타데이터.** `DECK_ID`·`DECK_TITLE`·`SUBJECT`가 `auto`이면 자료(또는 `MAIN_TOPIC`)에서 정한다: `deck.id`는 내용을 요약한 영문 소문자 snake_case(예: `os_process_scheduling_01`, 2~5 단어, 끝에 `_01`), `deck.title`은 출력 언어로 쓴 사람이 읽는 제목, `deck.subject`는 과목·분야명(예: `Operating Systems`). 값이 직접 지정되어 있으면 그대로 쓴다. 어느 경우든 Import 시 그 `deck.id`가 없으면 새 덱으로 만들어지고, 있으면 그 덱에 추가·갱신된다.
7-2. **출제 모드.** `SOURCE_MODE`가 `provided_materials`이면 첨부 자료(PDF·교안·본문)만을 근거로 출제하고, 자료가 전혀 없으면 JSON 대신 자료를 요청한다. `general_knowledge`이면 자료 없이 **`MAIN_TOPIC`과 `SUBTOPICS`에 대한 일반적·교과서적 지식**으로 출제한다: 소주제가 여럿이면 문항을 소주제별로 최대한 고르게 배분하고(각 문항의 `tags`에 해당 소주제를 넣는다), 논쟁적·버전 의존적·최신 사실은 피하며 널리 합의된 내용만 묻는다. 이 모드에서는 `source`·`references`·위치 표기를 넣지 않는다(규칙 6). `AUDIENCE_LEVEL`이 지정되면 난이도·용어·전제 지식의 기준으로 삼고, `-`이면 자료/주제가 전제하는 수준을 따른다.
8. **출력 언어.** `OUTPUT_LANGUAGE`가 `auto`이면 첨부된 입력 자료(PDF·교안·본문)의 **대부분을 차지하는 언어**로 `prompt`, 선지, 해설, 힌트, 모범답안, 루브릭을 모두 작성한다. 자료가 여러 언어로 섞여 있으면 분량이 가장 많은 언어를 택하고, 전문 용어·고유명사·코드·수식 기호는 원문 표기를 유지한다. 자료가 없고 주제만 주어지면 주제 설명에 쓰인 언어를 따른다. `OUTPUT_LANGUAGE`에 특정 언어 코드가 있으면 그 언어를 우선한다. 선택한 언어를 `deck.language`에 BCP-47 코드로 기록한다.

## REPRESENTATIONS (텍스트로 직렬화되는 모든 표현 — 적절할 때만)

모든 텍스트 필드(`prompt`, 선지·항목·조각·진술의 `text`, `explanation.*`, `hint`, `modelAnswer`, `back`, 루브릭 `guidance`, `steps[].prompt`)는 Markdown으로 렌더링되며, 아래 표현을 **문자열 안에 그대로** 넣을 수 있다. 문자열 안의 줄바꿈은 `\n`, 백슬래시는 `\\`로 이스케이프한다.
- **GFM Markdown**: 굵게/기울임, 목록, 번호 목록, 표(`| a | b |`), 인용, 인라인 코드, 링크. 표는 비교·사양·데이터를 보여줄 때.
- **코드 블록**: ```` ```python ```` 처럼 언어를 지정하면 구문 강조된다(복사 버튼 제공). 코드 읽기·출력 예측·오류 찾기 문항에.
- **수식**: `$...$`, `$$...$$` (KaTeX). 화학식은 `$\\ce{H2O}$`, `$\\ce{2H2 + O2 -> 2H2O}$` (mhchem).
- **다이어그램**: ```` ```mermaid ```` 블록 — flowchart, sequenceDiagram, classDiagram, stateDiagram-v2, erDiagram, gantt, pie, mindmap, timeline, gitGraph. 과정·상태 전이·구조·관계·시퀀스를 묻거나 설명할 때 글보다 명확한 경우에만. 노드 레이블에 특수문자가 있으면 따옴표로 감싼다(`A["x (y)"]`).
- **벡터 그래픽**: ```` ```svg ```` 블록에 **자기완결적 inline SVG**(`<svg viewBox=... xmlns=...>…</svg>`, 4 KB 이하, `<script>`·외부 참조·`href` 금지). 기하·회로·그래프 개형·단순 도형처럼 Mermaid로 표현하기 어려운 시각 자료에. 색은 2~3가지, 텍스트는 `<text>`로.
- **이미지**: 자료에 공개 URL이 있을 때만 `![설명](https://...)`. 존재하지 않는 URL이나 "그림 참조" 식 언급을 지어내지 않는다.
- **HTML**: Markdown으로 표현하기 어려운 것(셀 병합 표 `rowspan/colspan`, `<mark>` 강조, `<sup>/<sub>`, `<details><summary>` 접기, `<ruby>` 독음, 색/정렬을 위한 `style` 속성, inline `<svg>`)은 HTML을 문자열에 직접 써도 된다. 앱이 허용 목록으로 sanitize하므로 `<script>`, `<iframe>`, `on*` 이벤트 핸들러, `javascript:` URL, 폼 요소는 제거된다 — 넣어도 소용없으니 쓰지 않는다. 가능하면 Markdown을 우선하고, HTML은 꼭 필요한 부분에만 최소로 쓴다.

**사용 원칙 (매우 중요):** 이런 표현은 평가하려는 내용이 **그 표현으로 더 정확하게 전달·측정될 때만** 쓴다. 모든 덱이나 모든 문항에 골고루 넣을 필요가 전혀 없으며, 장식용 도식이나 내용 없는 표는 금지다. 글로 충분한 것은 글로 쓴다. 도식이 답을 누설하지 않는지(예: 상태 전이를 묻는 문항의 prompt에 정답 전이가 그려진 Mermaid) 반드시 확인한다. 선지(`text`)에 넣을 때는 선지들끼리 표현 방식이 비슷해야 한다(한 선지만 도식이면 단서가 된다).

## PEDAGOGY / QUESTION QUALITY

- 단순 재인(recognition)이 아니라 장기 기억 인출(retrieval), 개념 간 구별, 메커니즘 이해, 반례 판단, 계산·적용·문제 해결을 평가한다.
- 객관식 distractor는 같은 단원에서 실제 혼동하기 쉬운 유사 개념을 활용한다. 개념을 섞되 논리상 오답임이 분명해야 하고 중의적 정답을 절대 만들지 않는다.
- **금지되는 값싼 단서**: 오답에만 극단·범주 부사어('항상', '절대', '모든', '오직', '전적으로', '반드시', '불가능', '보장', '어떤 경우에도', always/never/all/none/only/exclusively/entirely/completely/universally/necessarily/must/impossible/guaranteed)를 쓰는 것, 정답만 더 길고 정교하거나 더 온건하게 쓰는 것, 정답이 규칙적으로 같은 위치에 오는 것, 문법·용어·확신도가 선지마다 다른 것. 극단 표현은 자료가 명시적으로 뒷받침하는 핵심 조건일 때만 쓰고, 그 경우에도 정답과 오답에 고르게 분포시킨다.
- **인지 수준 목표**(자료가 허용하는 범위에서): 사실 회상 ~15%, 개념 이해 ~20%, 적용 ~30%, 다단계 분석 ~25%, 개념 통합 ~10%. 난이도(쉬움 ~20% / 보통 ~45% / 어려움 ~35%)와 인지 수준을 예측 불가능하게 섞는다. **난이도는 추론의 깊이에서 나와야 하며**, 긴 문장·난해한 구문·필수 조건 생략으로 만들지 않는다.
- **유형 비율은 지침이지 할당량이 아니다 (매우 중요).** `QUESTION_TYPE_TARGET`은 내용이 허락할 때 따르는 대략의 분포이며, 어떤 경우에도 비율을 맞추기 위해 문항을 만들지 않는다. 각 내용마다 **그 내용을 가장 정확하게 측정하는 유형**을 먼저 고르고, 그 결과 분포가 목표에서 벗어나면 벗어난 채로 둔다. 금지: 순서가 없는 내용을 `ordering`으로, 짝이 없는 내용을 `matching`으로, 단일 사실을 `multiple_choice`로, 서술할 가치가 없는 내용을 `essay`로 비트는 것, 빈칸이 자연스럽지 않은 문장을 `cloze`로 만드는 것, 특정 유형의 칸을 채우려고 사소하거나 억지스러운 문항을 추가하는 것. `REQUIRE_ALL_EIGHT_TYPES`도 같은 원칙 아래에 있다: 어떤 유형에 자연스럽게 맞는 내용이 자료에 없으면 그 유형은 **빼고**, 그 자리는 가장 적절한 핵심 유형으로 낸다. 비율·유형 다양성보다 **문항 하나하나의 타당성**이 항상 우선한다.
- **자료 균형**: 첨부 자료가 여럿이면 길이와 무관하게 문항 수를 최대한 균등 배분한다(4개 자료 → 각 5문항). 긴 자료, 슬라이드가 자세한 자료, 문제로 만들기 쉬운 주제, 자료에 자주 반복되는 개념을 편애하지 않는다. 여러 자료를 통합하는 문항은 주 자료 하나로 집계한다.
- **스템 형식**: "관찰된 결과를 가장 잘 설명하는 것은?", "주어진 조건에서 따라 나오는 결론은?", "이 동작을 만드는 메커니즘은?", "결과를 지정된 방식으로 바꾸는 수정은?"처럼 조건이 명확한 문제 상황을 세운다. '가장 적절한'은 기준이 하나의 답을 결정할 때만 쓰고, "옳지 않은 것은?" 류 부정형 스템을 난이도 대용으로 남용하지 않는다. 한 문항이 다른 문항의 답을 누설하지 않게 한다.
- 매 문항은 가능한 경우 '왜 정답인가'뿐 아니라 '오답은 어떤 오개념에서 나왔나'를 밝혀라. 선택지별 `explanation`을 넣을 수 있다.
- 교안/챕터 출현 순서대로 문제를 배치하지 않는다. 모든 범위를 가급적 고르게 포함하고 유형·난이도·주제를 섞는다.
- 문항 수가 충분하면 정답 선택지 위치(a~e)와 OX의 true/false 비율을 대략 균형 있게 한다(문항 2~3개 때문에 완전균등을 강요하지 않는다).
- 배경 지식 없이 문항을 읽어도 요구 사항과 답변 범위가 이해되도록 명확하게 쓴다.
- 숫자, 공식, 기준, 정의를 묻는 문항은 단위·가정·조건 명시. 근거가 불확실하면 출제하지 않는다.
- `estimatedSeconds`와 `difficulty`를 실제 문항 해결 부담에 맞게 부여하라. 엄밀한 실험값처럼 보이게 하지 않는다.

## TYPE-SPECIFIC RULES

> **유형 선택의 대원칙 (최우선):** 평가하려는 내용이 유형의 구조와 자연스럽게 맞을 때만 그 유형을 쓴다. 비율을 맞추려고 내용을 비틀거나, 다른 유형으로 더 잘 묻는 내용을 특정 유형에 욱여넣는 것은 **절대 금지**다. 아래 비율·분포 목표는 모두 "자료가 자연스럽게 허용하는 범위에서"만 적용된다. 애매하면 더 단순한 유형을 쓴다.

### 선지가 있는 유형의 오답(distractor) 설계 — single_choice, multiple_choice, two_tier, cloze_select, statement_set, categorize에 적용
오답은 **불완전하게 이해한 학생에게 그럴듯해야** 하며, 피상적 어휘 패턴으로 걸러져서는 안 된다. 다음 기법을 문항에 맞게 골라 쓴다(모든 기법을 기계적으로 다 쓰지 않는다):
A. 메커니즘 교체 — 개념 A의 정확한 메커니즘을 개념 B에 귀속. B. 정의–역할 불일치 — 정확한 정의에 인접 개념의 기능·목적·한계를 결합. C. 부분 정답 — 여러 주장 중 일부는 맞지만 핵심 관계 하나가 틀림. D. 인과 역전. E. 조건 오적용 — 전제가 충족되지 않는 상황에 유효한 원리를 적용. F. 경계 조건 혼동 — 범위·시점·임계값·제약에 대한 잘못된 가정. G. 잘못된 통합 — 각각 타당한 두 원리를 결합해 무효한 결론. H. 근사 정답 계산 — 잘못된 분모, 역비율, 누락된 인자, 단위 불일치, 잘못된 가정의 공식 적용.
요구 조건: 모든 오답은 문항 조건 아래에서 **명확히 식별 가능한 실질적 오류** 하나를 담는다. 정답은 "덜 틀린 것"이 아니라 **증명 가능하게 옳아야** 한다. 선지들은 길이·문법 구조·용어의 구체성·기술적 세부·확신도·설명 깊이가 비슷해야 하며, 정답이 반복적으로 더 정밀·온건·포괄적으로 보이면 안 된다. 개념적으로 가까우되 복수 정답·애매한 표현·불분명한 가정·단순 논쟁거리는 금지. "모두 맞다/모두 틀리다" 선지 금지.

### 유형별 지침

- `single_choice`: `choices` 최소 2개(설정에 따라 5개 권장), 각 `{id,text,explanation?}`, `answer: {"choiceId":"..."}`. **정답 ID는 반드시 choices에 존재**. 정답은 정확히 하나. 위 distractor 설계 규칙을 그대로 적용하고, 각 오답의 `explanation`에 그 오답이 담은 오개념을 적는다. 덱 전체에서 정답 위치(`a`~`e`)를 최대한 고르게 배분하고(5지선다 20문항 → 각 4개 근처), 난이도·출처와 정답 위치가 상관하지 않게 한다. 앱은 보기 순서를 섞어 보여주므로 위치 단서는 어차피 제거되지만, 선지 **문장** 자체의 단서는 반드시 없애야 한다.
- `multiple_choice`: 정답이 최소 2개이면서 오답도 최소 1개. `answer: {"choiceIds":["...", "..."]}`. 정답 집합을 빠짐없이 명확히 정의. 선택지마다 독립적으로 참/거짓 판정 가능해야 한다. 덱 안에서 정답 개수(2~4)를 달리해 개수가 단서가 되지 않게 하고, 오답은 '부분 정답'·'조건 오적용'형으로 만들어 정답 선지들과 어휘·구조가 같아 보이게 한다.
- `true_false`: `answer: {"value":true}` 또는 `false`(실제 JSON boolean). 질문 문장은 애매하지 않게, 한 문장에 **하나의 주장**만. 거짓 진술은 극단 부사어가 아니라 메커니즘 교체·인과 역전·조건 오적용 같은 실질적 오류로 만든다. 덱 전체에서 참/거짓을 대략 반반으로.
- `short_answer`: `answer: {"acceptedAnswers":["...", "..."]}`. 표현상 동등한 표기(영문 대소문자, 단위 표현 등)는 가능한 경우 모두 포함. 의미가 비슷하기만 한 오답은 정답 목록에 넣지 말 것. 자동 채점은 엄격한 문자열 기준임을 고려. **답이 유일하고 표기가 고정된 것**(용어, 수치, 기호)에만 쓰고, 여러 표현이 다 맞는 설명형 답은 `recall_card`나 `essay`로 낸다.
- `essay`: `answer: {"modelAnswer":"...", "maxScore":10, "rubric":[{"criterion":"...", "maxPoints":..., "guidance":"..."}]}`. 점수 배점의 합계는 `maxScore`와 정확히 일치. 모범답안에 채점 근거를 충분히 포함한다. AI 자동 채점 전제 금지. 루브릭 기준은 서로 다른 추론 요소(메커니즘, 조건, 결과, 반례 등)로 나누고, `guidance`에는 **어떤 근거가 점수를 받는지**를 구체적으로 쓴다. 통합·분석 수준 문항에 적합하다.
- `cloze`: `prompt`에 **정확히** `{{b1}}`, `{{b2}}`처럼 빈칸 삽입. `blanks: [{"id":"b1", "acceptedAnswers":[...]}, ...]` 와 ID가 1:1 일치. 너무 많은 빈칸 금지(1~3개 권장). 개념을 담은 토큰을 비우고(사소한 단어 금지), 문맥만으로 답이 유일하게 결정되어야 한다. 표기 변형이 많으면 `cloze_select`로. `{{id}}`는 일반 문장뿐 아니라 **GFM 표 셀, HTML 표 셀, 목록 항목, ```` ```mermaid ````/```` ```svg ```` 도식의 노드 레이블·텍스트** 안에도 넣을 수 있다(표 빈칸 채우기, 도식 빈칸 채우기, 차트 해석). 도식 안의 빈칸은 앱이 ①②③ 번호 라벨로 바꿔 그리고 도식 아래에 번호별 입력칸을 보여준다(번호는 `blanks` 순서). 같은 placeholder는 한 번만 쓸 수 있으므로 mermaid에서 같은 노드를 여러 줄에서 참조하면 `state "{{b1}}" as W` / `W["{{b1}}"]`처럼 별칭을 만들어 레이블에 한 번만 넣는다. 일반 코드 펜스(```` ```js ```` 등)와 인라인 코드 안의 `{{…}}`는 빈칸이 아니라 코드 그대로 표시된다.
- `ordering`: `items:[{"id":"...","text":"..."}, ...]`, `answer: {"orderedIds":[...]}`. 단계들의 순서가 하나로 결정되는 과정만 출제. orderedIds는 items의 모든 ID를 정확히 한번씩 포함. 항목의 입도(granularity)와 문장 길이를 비슷하게 맞춰 길이·형식이 순서 단서가 되지 않게 하고, 항목 문구에 '먼저', '마지막으로' 같은 순서 단어를 넣지 않는다.
- `matching`: `left` / `right` 각각 id,text 배열, `answer: {"pairs":[{"leftId":"...", "rightId":"..."}, ...]}`. 모든 좌측 ID와 우측 ID가 **1:1 bijection**이고 중복 배정 없음. 연결 규칙이 분명한 개념만 출제. 우측 항목은 같은 개념군의 서로 가까운 것들로 구성해 소거법만으로 풀리지 않게 하고, 우측 문구는 좌측 단어를 그대로 반복하지 않는다.

## EXTENDED TYPES (선택, 자연스러울 때만)

`ALLOW_EXTENDED_TYPES`가 true이면 아래 8종을 **추가로** 쓸 수 있다. 이 유형들은 핵심 8종보다 상호작용이 많고 학습 상태를 더 세밀하게 측정하지만, **절대 억지로 쓰지 않는다.** 규칙: (1) 평가하려는 내용이 그 유형의 구조와 자연스럽게 맞을 때만 사용한다. (2) 유형별 비율을 맞추려고 문제를 비틀거나, 핵심 유형으로 더 잘 묻는 내용을 확장 유형으로 바꾸지 않는다. (3) 조금이라도 어색하면 핵심 유형(`single_choice`, `short_answer` 등)으로 낸다. (4) 확장 유형은 `QUESTION_TYPE_TARGET`·`REQUIRE_ALL_EIGHT_TYPES`의 집계 대상이 아니며, 하나도 쓰지 않아도 된다.

- `numeric`: 정답이 **하나의 수**이고 허용 오차가 의미 있을 때(계산·단위 변환·추정). 스템에 단위·정밀도·가정을 명시하고, 오차는 반올림 관례를 반영해 정한다. 다단계 계산이면 `stepwise`를 고려한다. `answer: {"value": 12.5, "tolerance": 0.1, "relativeTolerance": 0.02, "unit": "ms"}` — `tolerance`(절대)·`relativeTolerance`(비율)는 선택, 둘 다 없으면 정확히 일치. 학습자는 숫자만 입력한다.
- `cloze_select`: 빈칸마다 **보기 중 고르는** 빈칸 문제. 각 빈칸의 보기들은 같은 품사·형태의 인접 개념(메커니즘 교체 짝)으로 구성해 문법만으로 걸러지지 않게 한다. 자유 입력(`cloze`)이 표기 차이로 채점이 불안정할 때 사용. `prompt`에 `{{id}}`, `blanks: [{"id":"b1","options":[{"id":"a","text":"..."}],"answerOptionId":"a"}]`. 모든 빈칸은 placeholder와 1:1. `cloze`와 같이 표 셀·HTML 표·mermaid/svg 도식 안에도 `{{id}}`를 둘 수 있다(도식 안 빈칸은 ①②③ 라벨 + 도식 아래 선택칸으로 표시; 별칭으로 한 번만 참조).
- `statement_set`: **같은 주제의 여러 진술**을 각각 참/거짓 판단. 참/거짓을 섞어 배치하고, 거짓 진술마다 구체적 오개념(메커니즘 교체·인과 역전·경계 조건)을 하나씩 담아 `explanation`에 적는다. 극단 부사어로 거짓을 만들지 않는다. 관련 사실이 3~8개 묶일 때만. `statements: [{"id":"t1","text":"...","value":true,"explanation":"..."}]`. 진술은 독립적으로 판단 가능해야 한다.
- `categorize`: 항목들을 **상호 배타적 범주**로 분류. 범주는 자료가 제시한 기준으로 나누고, 항목에는 그 기준을 실제로 이해해야 분류되는 **경계 사례**를 포함한다(자명한 항목만으로 채우지 않는다). `categories: [{"id":"c1","label":"..."}]`, `items: [{"id":"i1","text":"...","categoryId":"c1"}]`. 범주 2~8개, 항목 2~30개, 각 항목의 범주는 논란 없이 하나.
- `two_tier`: 정답 **그리고 그 근거**를 함께 고르는 2단계 객관식(추측 배제). 근거 보기에는 각 오답 선택이 비롯되는 실제 오개념을 넣어 근거 단계가 '이해 vs 추측'을 가르게 하고, 정답 근거가 가장 길거나 정교해 보이지 않게 한다. '왜?'를 묻는 개념 이해·분석 문항에 적합. `choices`, `reasons`, `answer: {"choiceId":"a","reasonId":"r1"}`. 오답 근거는 실제 오개념이어야 한다.
- `recall_card`: 앞면(`prompt`)을 보고 뒷면(`back`)을 떠올리는 **순수 회상 카드**(Anki 기본형). 앞면은 정확한 단서 하나, 뒷면은 핵심 용어를 **굵게** 표시한 자기완결적 설명으로 쓰고, 뒷면에 없는 내용을 앞면이 요구하지 않게 한다. 정의·공식·핵심 키워드처럼 "설명할 수 있는가"가 중요할 때. 자동 채점은 없고 학습자가 뒷면과 비교해 스스로 표시한다. 표기가 고정된 짧은 답(용어·연도·기호)에는 `answer: {"acceptedAnswers":[...]}`를 넣어 자동 채점할 수 있다.
- `stepwise`: **여러 단계의 계산/추론**을 단계별 단답으로 확인해 어디서 막히는지 측정. 단계는 실제 풀이 경로를 따르고, 각 단계의 답은 앞 단계가 주어졌을 때 유일하게 결정되며, 앞 단계의 `prompt`가 뒤 단계의 답을 누설하지 않게 한다. 다단계 분석 문항에 적합. `steps: [{"id":"s1","prompt":"...","acceptedAnswers":["..."],"explanation":"..."}]` 2~10단계, 각 단계 답은 문자열 정확 일치 기준.
- `highlight`: 지문/코드를 조각(`segments`)으로 나누고 **해당하는 조각을 모두 선택**(오류 찾기, 핵심 근거 찾기). 정답이 아닌 조각도 그럴듯한 근사 표현이어야 하며, 정답 조각은 실제 오류·근거가 있는 바로 그 위치여야 한다. 조각 길이를 비슷하게 맞춰 길이가 단서가 되지 않게 한다. `segments: [{"id":"w1","text":"..."}]`(원문 순서 유지), `answer: {"segmentIds":[...]}`. 조각은 의미 단위로 나누고 정답 외 조각이 반드시 있어야 한다.

## ADVERSARIAL SELF-REVIEW (출력 전, 모든 문항)

최종 JSON을 내기 전에 **모든 문항**을 세 관점에서 내부 검토하고, 실패하면 고친 뒤에만 출력한다.
- **검토자 1 — 해당 분야 전문가**: 정답이 정확히 하나이고 증명 가능한가, 자료의 개념을 올바르게 적용했는가, 자료에 없는 사실을 전제하지 않았는가, 모든 오답이 식별 가능한 개념적 오류를 담는가, 전제·조건이 애매하지 않은가.
- **검토자 2 — 시험 요령만 아는 학생**: 교과 지식 없이 극단·범주 표현, 유난히 길거나 자세한 선지, 확신도 차이, 문법 불일치, 낯선 용어, 반복되는 문장 구조, 명백히 비현실적인 선지, 정답만 온건한 표현 등 **어휘 단서만으로** 정답을 맞히거나 오답을 소거할 수 있는가. 가능하면 선지를 다시 쓴다. 특히 'always/never/only' 류 때문에 틀린 오답은 교체한다.
- **검토자 3 — 적대적 추론가**: 각 오답에 대해 옹호 논리를 세워 보고 그것이 어디서 무너지는지 확인하며, 정답에 대한 반례를 만들어 본다. 복수 정답이 남으면 스템이나 선지를 수정한다. 필수 조건을 빼서 어렵게 만들지 않는다 — 이상적인 문항은 **맞히기는 어렵지만 채점은 명백**하다.
- **덱 수준 감사**: 유형마다 "이 내용에 이 유형이 자연스러운가"를 다시 묻고 억지스러우면 핵심 유형으로 바꾼다. 유형 비율이나 8종 포함을 맞추려고 비튼 문항이 하나라도 있으면 **비율을 포기하고** 그 문항을 자연스러운 유형으로 되돌리거나 더 가치 있는 문항으로 교체한다. 정답 위치 분포(객관식), 참/거짓 비율, 자료별 문항 수, 난이도·인지 수준 분포, 문항 간 답 누설 여부를 점검한다.

## BEFORE OUTPUT: SILENT SELF-VALIDATION

아래 조건을 모두 검증하고 실패하는 질문은 스스로 고친 후 최종 JSON만 출력하라.

- 질문 수 `NUMBER_OF_QUESTIONS`와 일치. 유형 비율은 대략 따르되 지침일 뿐이며, 비율을 맞추려고 억지로 유형을 바꾸거나 끼워 넣은 문항이 없어야 한다. REQUIRE_ALL_EIGHT_TYPES인 경우 자연스럽게 맞는 내용이 있는 유형만 각 최소 1개(총 문제 수가 8개 이상일 때); 맞는 내용이 없는 유형은 빼도 된다.
- 공통 필수 속성 누락 없음, 속성 타입 오류 없음, 모든 설명이 실제 정답을 뒷받침.
- 질문 ID/선택지 ID/빈칸 ID/정렬 ID/매칭 ID 참조 및 중복 없음.
- 복수정답 선택지 중 적어도 하나가 오답, 최소 2개 정답.
- 클로즈 placeholder와 blanks 완전 일치. ordering은 정확한 permutation. matching은 완전한 bijection.
- 서술형 루브릭 총합 == maxScore.
- 확장 유형을 썼다면: 그 유형이 아니면 묻기 어려운 내용인지 다시 확인하고, 억지스러우면 핵심 유형으로 바꾼다. `cloze_select` placeholder=blanks, `categorize` categoryId 유효, `two_tier` choiceId/reasonId 유효, `highlight` segmentIds ⊂ segments.
- 시험 문제의 정답이 `prompt`/보기에 무심코 누출되지 않는지 점검.
- 모든 LaTeX가 `$`/`$$`로 감싸져 있고, JSON 안에서 백슬래시가 이중 이스케이프되어 있으며, KaTeX 미지원 명령이 없는지 점검.
- Mermaid/SVG/표/코드 블록을 썼다면: 그 표현이 꼭 필요한지, 문법이 유효한지(Mermaid는 첫 줄에 다이어그램 종류, SVG는 `viewBox`와 `xmlns`), 정답을 누설하지 않는지, 선지 간 표현이 균형 잡혔는지 점검.
- JSON parser가 읽을 수 있는 순수 JSON, 추가 텍스트 없음.
- `question-batch.schema.json` 검증 통과를 내부적으로 다시 확인.

이제 입력한 교안/주제만 이용하여(`general_knowledge` 모드면 `MAIN_TOPIC`·`SUBTOPICS`에 대한 일반 지식으로), 위 출력 언어 규칙에 따른 언어로 `schemaVersion`, `deck`, `questions`를 갖는 JSON을 출력하라. 최종 응답 첫 글자는 `{`이고 마지막 글자는 `}`이어야 한다.
